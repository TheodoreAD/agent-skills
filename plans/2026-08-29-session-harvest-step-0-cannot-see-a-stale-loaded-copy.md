# Step 0 passes cleanly while the session reasons from an outdated skill

Consolidate with `plans/2026-08-29-session-harvest-stale-install-third-case.md` — same step, and
that plan is already enumerating the causes of a step 0 difference. This is the case where there is
**no** difference and the check is still not telling the truth.

## Context

Step 0 diffs the installed skill against the checkout. It has three known outcomes, two of them
described by the plan above: clean checkout ahead of the install (a real stale install), and a dirty
checkout (another session's unpushed work). A fourth exists, and it is the one the diff cannot see.

Confirmed 2026-08-29, in a `repo-tasks` session:

- `plan-docs`'s `SKILL.md` was loaded into the session's context early in the session.
- `agent-skills` commit `bd6c55d` landed at 19:58, rewriting that skill's pre-push guidance: the
  gate before the store's first push is `scan --mode history`, not `scan --mode tree`. The installer
  had already run, so the file on disk was current.
- The session, reasoning from what it held in context, told the user the installed skill was
  **behind** its source and filed that claim into a plan.
- Step 0's own check at the start of the harvest: `diff -rq` between `~/.agents/skills/plan-docs/`
  and the checkout — identical apart from `__pycache__`. Exit 0. The install had been right the
  whole time.

So the diff answered the question it was asked, and the question was the wrong one. What was stale
was neither the install nor the checkout but **the copy in the session's context**, frozen at load
time, which no filesystem comparison can reach.

[PITFALL: this failure inverts the one step 0 was written for. A stale install makes the session run
old _code_; a stale loaded copy makes it apply old _instructions_ while the code is current — and it
produces confident, specific, wrong statements about the very skills the harvest is auditing. The
wrong claim here was about which scan mode gates a push, which is a confidentiality gate: acting on
the loaded wording would have run `--mode tree` before publishing a store and got a clean answer
from the check that does not look at history.]

## Why it is worth a check rather than a caveat

The window is not exotic. This machine runs parallel sessions on `agent-skills` continuously, so any
session lasting more than an hour is likely holding at least one skill that has since changed. The
tell is cheap: the skill's own file mtime, or a `git log -1 --format=%ci` on its path in the
checkout, compared against when the session started.

## Recommended direction

Rough; the mechanism matters less than the check existing.

1. **Add a fourth outcome to step 0**: identical files do not mean the session's understanding is
   current. Check whether the skill changed _since this session started_ —
   `git -C <checkout>
   log -1 --format=%ci -- skills/<name>/` against the session's own start time
   — and if it did, re-read the installed `SKILL.md` from disk before relying on it.
2. **State the consequence in one clause**, since that is what makes anyone run it: a stale loaded
   copy produces specific wrong claims about the skills being audited, and the harvest is the report
   nobody re-checks.
3. Fold into the three-cause paragraph the sibling plan proposes rather than adding a step — it is a
   fourth branch of the same check, not a new one.
