# Judging a dependency: the traps, and the methodology behind the numbers

Loaded when a candidate is actually being judged. `SKILL.md` carries the bar and the command; this
carries the reasoning, and every entry here is something that produced a wrong number or a wrong
judgement in a real comparison before it was known.

## Traps that produce a wrong number

**A bot dominates the bus factor.** `renovate[bot]` was 70% of one project's commits over a year,
which reads as a catastrophic bus factor and is dependency bumps. Excluding `[bot]`, `dependabot`,
`renovate` and `pre-commit-ci` reversed the finding — that project turned out to have the _better_
human distribution of the two. Any contributor metric has to filter bots. Measured again 2026-09-02
on `agronholm/anyio`: `pre-commit-ci[bot]` at 40 commits was the second-largest committer in the
window, ahead of every human but the maintainer.

**GitHub's licence field reports one licence for a dual-licensed project.** The API said `GPL-3.0`
for a project shipping `LICENSE`, `LICENSE.lesser` and a `LICENSE.dual` whose first line says either
may be chosen. Taking the API at face value would have wrongly disqualified it on copyleft grounds.
Check the licence files in the clone, not the field.

**A raw test-to-source ratio is meaningless where a project has a large mechanical binding layer.**
One candidate looked like 0.28 against a peer's 0.81 — until 71% of its source turned out to be
one-class-per-API-object modules. Against hand-written code the same project was 1.07, i.e. better
than the peer rather than a third as good. Segment the source before dividing; `--generated <glob>`
is where that judgement goes, and the report states it rather than guessing.

**`open_issues_count` counts pull requests, and survives a repo with no issue tracker at all.**
Confirmed 2026-09-02: `encode/httpx` reports `has_issues: false` and `open_issues_count: 143`, every
one of which is a PR. "Open issues relative to project size" computed off that number compares a
review backlog against a support backlog.

**A recent-closed sample can contain zero issues.** Same session, same repo: 300 closed items across
three pages of the issues endpoint, not one of them an issue. A median of `None` there is
indistinguishable from a project that closes nothing, so the sample composition has to travel with
the median. On `pallets/click`, which does use its tracker, the 50 most recent closed items held 4
issues — obtainable, and thin enough that the number deserves its denominator printed beside it.

**PyPI's release map holds pre-releases, and a moving dev line is not a moving stable line.**
Confirmed 2026-09-02 on `httpx`: the three most recent uploads are `1.0.dev4`, `1.0.dev5` and
`1.0.dev6`, so counting the map gave "4 releases in the last year, last one 1 day ago" for a project
whose stable line is `0.28.1` from 2024-12-06 — 634 days earlier. Both numbers are true and only one
of them answers "is this maintained for me". `.post` releases are real releases and stay counted.

**A `pyrightconfig.json` `include` is ignored when the checker is pointed at a shared scratch
directory**, so a per-candidate measurement silently becomes the sum of every file sitting beside
it. Caught 2026-08-30 when a 25-line file reported 208 warnings. Put each sample in its own
directory with its own config, and assert `filesAnalyzed` is what you expected before reading any
count.

**A search summary will assert implementation details the source does not support.** One candidate
is widely described, including by its own marketing, as having autogenerated API bindings. There is
no generator in the repository and no generated-file header. It may well be generated by a tool kept
elsewhere, but the claim could not be confirmed from the source, and a comparison resting on it
would have been resting on nothing. This is the skill's "grep the real source" rule earning itself
again.

**The library's shallow clones cannot answer a history question.** `--depth 1` is the convention
there and it is right for reading current source, but constraint archaeology needs
`git fetch --deepen <n>` first. `git log -p -- pyproject.toml` on a depth-1 clone returns one commit
and looks like a project that has never changed its pins. `package_health.py` reports the clone as
shallow for exactly this reason.

## Traps that produce a wrong judgement from correct numbers

**A version cap is not a cost until its historical lag says it is.** A dependency pinning `foo<2.14`
looks like it will hold the consumer back, and the way to find out is archaeology rather than
argument: trace the constraint through that project's own git history and line each widening up
against the capped project's release dates.

Measured 2026-08-30 on a candidate capping pydantic:

| capped release | published  | cap widened | lag     |
| -------------- | ---------- | ----------- | ------- |
| 2.7.0          | 2024-04-11 | 2024-04-22  | 11 days |
| 2.8.0          | 2024-07-01 | 2024-07-06  | 5 days  |
| 2.9.0          | 2024-09-05 | 2024-09-09  | 4 days  |
| 2.10.0         | 2024-11-20 | 2024-11-23  | 3 days  |
| 2.11.0         | 2025-03-27 | 2025-03-29  | 2 days  |
| 2.12.0         | 2025-10-07 | 2025-10-08  | 1 day   |
| 2.13.0         | 2026-04-13 | 2026-05-03  | 20 days |

Median five days. That is a rolling ceiling maintained deliberately, not a wall — and the one time
the cap was held on purpose, the commit says why (an upstream release breaking a Python version they
still supported), which is a project doing its job rather than neglecting it. Without this table the
cap reads as a disqualifier; with it, it reads as a maintenance signal in the candidate's favour.

**Say where a cap binds.** A constraint reached only through an optional extra or a dev group binds
the development lockfile; it never reaches the distributed artifact, whose own
`[project.dependencies]` stay as written. Those are different costs and conflating them overstates
the second one. Establish which it is before weighing it at all.

**Measure whether a typing gap is _coverable_, not just that it exists.** A candidate produced nine
`reportUnknown*` diagnostics under the consumer's own checker because its central class is generic
over six parameters and is normally written bare. Writing the six arguments once, as a `TypeAlias`,
took the same sample to zero errors and zero warnings. The gap was real and the cost was four lines
— and it had already been written into a recommendation as though it were structural. Always try the
fix and re-measure before scoring the gap.

**Prove offline-testability by removing the network, not by reading about it.** One candidate's
documentation describes dispatching updates without network access; its application object
nonetheless calls the API during startup, so a fake token raises before any handler runs. The
decisive test was replacing `socket.socket` with a function that raises and dispatching anyway — one
candidate passed untouched, the other needed a request-layer subclass. Neither library's docs said
this.

**Install size and dependency count can disagree, and neither alone is the footprint.** Measured in
two isolated virtualenvs: 14 MB across 12 packages versus 15 MB across 18. A conclusion drawn from
size alone said "equivalent"; from count alone, "half again as much". Report both, and resolve them
against what actually matters for the consumer — usually the transitive names, not the bytes.

## Why this lives here rather than in a skill of its own

[DECISION: `research-library` already owns "before fetching anything from the web, check the
library" and "grep the real source, don't trust docs/README prose". Judging a candidate dependency
is the same activity one step earlier, on the same material, reached by the same trigger. A separate
skill would compete with this one for that trigger, which is the failure mode this repo's authoring
rules are written against — two descriptions plausibly matching one request, with no way to predict
which fires.]

## What the script deliberately does not do

[DEFERRED: a `--compare` mode taking two or more candidates and emitting the table directly. Obvious
and desirable, and deliberately after the single-candidate path is right — the absolute bar is the
part that matters, and a comparison mode built first would quietly make the head-to-head the primary
output again.]

[DEFERRED: generalising beyond PyPI. The same questions apply to npm, crates.io and Go modules, and
the metric definitions would transfer with a different fetch layer. Not now; there is one ecosystem
in play and a premature abstraction over registries would be shaped by exactly one of them anyway.]

[DECISION: no download-count metric. PyPI's own stats come from BigQuery or pypistats.org rather
than the JSON API, so it is a second network dependency for a signal close to popularity — which
this whole approach says is weak. "Is anybody using this at all" is a legitimate question and a
different one from "is it the most popular"; when it needs answering, the dependents graph and the
issue tracker's traffic answer it better than a download count that CI mirrors inflate.]

[DECISION: `--clone` never clones. It reads a path the caller already has. Cloning on demand would
put entries in `$RESEARCH_HOME` as a side effect of an unrelated question, which is how a library
fills with material nobody chose to keep — and the library's own conventions require a `SOURCE.md`
beside every entry, which a side-effect clone would not write.]
